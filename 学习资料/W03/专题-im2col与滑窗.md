# 专题：卷积的两条向量化路线（滑动窗口 vs im2col）

> W3 任务 1 的知识底座。搞懂这一篇，卷积、池化、深度学习里的卷积层就是同一件事。

---

## 一、问题：怎么把"核在图上滑动"变成一次数组运算

卷积的定义是「核盖在每个位置，对应相乘再求和」。朴素写法：

```python
for y in range(H):
    for x in range(W):
        out[y, x] = np.sum(img[y:y+k, x:x+k] * kernel)
```

640×480、5×5 核：30 万位置 × 25 次乘加。**实测 910 ms**（W3 准备阶段的真实数据）。

瓶颈不在乘加次数，在 **Python 解释器逐次执行循环**。要提速就必须把"循环"变成"数组运算"。
问题只有一个：**核滑动时取到的那些窗口，能不能一次全部拿到？**

---

## 二、路线 A：滑动窗口（sliding_window_view）

```python
from numpy.lib.stride_tricks import sliding_window_view

padded  = np.pad(img.astype(np.float64), k//2, mode="reflect")  # pad 让输出尺寸不变
windows = sliding_window_view(padded, (k, k))                    # 关键：一次拿到全部窗口
out     = np.einsum("ijkl,kl->ij", windows, kernel)              # 一次算完
```

### 它为什么这么快：视图（view），不是复制

`sliding_window_view` **不复制数据**。它只改 stride，让同一个内存块被"看成"多个窗口：

```
内存里的图（一维）：  a b c d e f g h
窗口 1 看到的：        [a b c]
窗口 2 看到的：          [b c d]      ← 同一个 c，没有被复制两份
```

所以 `windows` 的形状虽然是 `(H, W, k, k)`，**实际占用的内存还是原图那么多**。
（你可以验证：`windows.base is padded` → True）

### `einsum` 下标怎么读

```python
np.einsum("ijkl,kl->ij", windows, kernel)
```

| 符号 | 含义 |
| --- | --- |
| `i`、`j` | 输出图的行、列——**保留** |
| `k`、`l` | 核的行、列——**求和消掉** |
| `->ij` | 输出只剩 i、j 两维 |

翻译成人话：**对每个 (i,j)，把 k×l 那 9（或 25）个数乘起来再加总**——正是卷积定义。
`einsum` 的好处是**你自己写出"保留哪维、消掉哪维"**，不用管中间怎么循环。

### 边界：四种 padding 模式对照

| 模式 | numpy 写法 | cv2 常量 | 特点 |
| --- | --- | --- | --- |
| 补零 | `mode="constant"` | `BORDER_CONSTANT` | 图像边缘变暗（人为引入 0） |
| 镜像（不含边） | `mode="reflect"` | `BORDER_REFLECT_101` | **cv2 默认**，"gfedcb\|abcdefgh\|gfedcb" |
| 镜像（含边） | `mode="symmetric"` | `BORDER_REFLECT` | "fedcba\|abcdefgh\|hgfedc" |
| 复制边缘 | `mode="edge"` | `BORDER_REPLICATE` | 边缘像素向外延伸，中值滤波用这个 |

**自测**（不看答案先答）：`np.pad([a,b,c], 2, mode="reflect")` 得到什么？
`symmetric` 呢？（答案：`reflect` → `c b | a b c | b a`；`symmetric` → `b a | a b c | c b`）

> 这个差别在 W3 的验收里**真的会影响分数**：用错模式 PSNR 会掉，而且差异集中在图像边缘一圈。

## 三、路线 B：im2col（image to column）

思路：把每个窗口**摊平成一行**，得到矩阵，然后用矩阵乘法一次算完。

```python
windows = sliding_window_view(padded, (k, k))     # (H, W, k, k)
cols    = windows.reshape(H * W, k * k)           # (像素数, k²)   ← 这一步会复制内存
out     = cols @ kernel.ravel()                   # (像素数,)     ← BLAS 矩阵乘
out     = out.reshape(H, W)
```

### 矩阵形态长什么样

```
                核摊平成一列
                [w00]
                [w01]
cols     ×      [w02]        =   out
(像素数, k²)    [...]
                [wkk]

每一行 = 一个位置上窗口里的全部像素
每一列 = 核里的一个系数
```

或者换个视角看（更直观的"摊平"）：

```
原图（3x3，核 2x2）        4 个窗口，每个 4 个数
a b c                      [a b d e]   ← 窗口在左上
d e f           →          [b c e f]
g h i                      [d e g h]
                           [e f h i]
```

这就是 im2col 后的矩阵。**每一行是一个窗口的像素**，行数 = 输出像素数，
列数 = 核大小²，然后一次矩阵乘得到所有输出。

### 代价与收益

| | 滑动窗口 | im2col |
| --- | --- | --- |
| 内存 | 视图，**不复制** | **复制**，涨 k² 倍（5×5 就是 25 倍） |
| 计算 | `einsum`（通用，不一定最优） | 矩阵乘（**BLAS，优化到极致**） |
| 实测 1920×1080 5×5 | 72.4 ms | **122.4 ms（这一版反而慢）** |
| 深度学习里的地位 | — | **工业标准**（还能上 GPU） |

> ⚠️ 注意上表的实测：**在这台机器的小核上，im2col 反而更慢**。
> 因为 k=5 时复制 25 倍数据的开销超过了矩阵乘的收益。
> 但 k 变大、或者上 GPU 时，im2col 的矩阵乘优势会碾压。
> **结论：没有绝对的"更快"，要实测**。这本身就是个好结论，写进报告。

## 五、可分离卷积（顺带一个优化技巧）

二维高斯核是**可分离**的：

```
exp(-(x²+y²)/2σ²) = exp(-x²/2σ²) × exp(-y²/2σ²)
```

所以「用 k×k 核卷积一次」= 「先用 1×k 横向卷积，再用 k×1 纵向卷积」。

| 写法 | 每个像素的乘法次数（k=5） |
| --- | --- |
| 二维核直接卷积 | 25 |
| 可分离（横 + 竖） | 5 + 5 = **10** |

**省 2.5 倍**。k 越大收益越大（k=9 时 81 → 18，省 4.5 倍）。

cv2 内部就是这么做的。你可以在任务 2 里把它当**挑战项**实现一下，测测差多少。

> 顺带一提：这也是为什么"任意核卷积"和"高斯/盒式滤波"在 cv2 里性能差很多——
> 后者能用可分离 + 积分图，前者只能老老实实逐窗口算。

<details>
<summary>答案</summary>

1. 视图。`windows.base is padded` 为 True；或 `windows.strides` 显示没有新分配。
2. `reflect` → `[3,2,1,2,3,2,1]`；`symmetric` → `[2,1,1,2,3,3,2]`
3. 结果不对。`"ijkl,lk->ij"` **不等于**把核旋转 180°——它是用转置后的下标去对齐窗口，
   得到的是另一种（错误的）收缩方式，实测与正确结果相差最大 8.0（20×20 小块上）。
   **规则：`einsum` 的下标顺序必须和两边维度语义一一对应，写反了不会报错，只会悄悄算错。**

> **一个必须知道的事实**：严格数学意义上的「卷积」要把核**翻转 180°**，
> 而 `cv2.filter2D` 做的是**相关（correlation，不翻转）**——这是图像处理库的惯例
> （PyTorch 的 `Conv2d` 也是相关）。
> 我实测验证过：同一个 Sobel 核，不翻转时与 cv2 完全一致（PSNR = inf），
> 翻转后掉到 20.0 dB。**所以 W3 里我们写的其实是相关，但习惯上叫卷积——这不是 bug，是整个领域的约定。**
> 因为核本身对称时（均值、高斯）两者没区别，只有非对称核（Sobel）才看得出差别。

4. 涨 k² 倍。因为矩阵乘能吃满 GPU/CPU 的算力，复制一次换大量计算是划算的（核大时）。
5. 5+5=10 次，比 25 次省 2.5 倍。
